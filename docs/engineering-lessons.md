# 前后端工程经验沉淀

这份笔记记录本项目已经验证过的前后端做法，后续迭代优先参考这里，避免重新讨论同一类工程取舍。

## 1. 先固定数据契约，再扩展界面

本项目的核心不是页面样式，而是 `Signal` 这类情报对象的稳定结构。前端、API、SQLite、静态导出版都围绕同一组字段工作：

- 时间、实体、公司、产品、标题、摘要
- 话题、话题模式、来源、域名、URL
- 证据层级、可信度、采集来源、AI 分类结果、确认状态

后续新增功能时，优先判断是不是需要扩展这个契约。如果只是展示方式变化，不要改数据库结构；如果确实要新增字段，要同步检查：

- `lib/types.ts`
- `db/001_init.sql`
- `lib/db.ts`
- `components/Dashboard.tsx`
- `scripts/export-static-dashboard.mjs`
- `data/signals.json`
- `前端展示版/data/signals.json`

## 2. 静态版和本地后端版要保持同源

这个项目同时保留两种形态：

- 本地 Next.js 版本：负责 SQLite、采集、报告生成和交互式查询。
- 静态快照版本：负责无后端展示、GitHub Pages 或离线分享。

经验是不要把静态版做成第二套业务逻辑。应该把 Next.js 里的稳定数据导出成静态快照，让静态版尽量只承担展示职责。刷新静态页面时使用：

```bash
npm run static:export
```

后续如果页面能力只依赖现有数据，优先同时支持两边；如果功能依赖密钥、数据库写入或后台采集，只放在本地 Next.js 版本里。

## 3. 前端状态按“视图意图”组织

Dashboard 的状态可以按用户意图分组，而不是按组件层级拆散：

- `mode`：总览、话题、公司。
- `view`：信号、矩阵、地图、采集。
- `query/topic/companyName`：当前筛选条件。
- `report`：报告生成相关状态。
- `collectorConfig/runs/sources`：采集状态。

这个结构的好处是新增入口时比较清楚：如果是筛选类功能，接入 `filteredSignals`；如果是采集类功能，接入采集状态；如果是报告类功能，接入 `report`。不要把同一个筛选条件复制到多个组件局部状态里。

## 4. 后端 API 保持薄层，复杂逻辑放到 lib

API route 只做三件事：

- 读取请求参数。
- 调用 `lib/*` 中的业务函数。
- 返回 JSON。

分类、采集、数据库映射、去重、报告生成都应该放在 `lib/` 或 `scripts/`。这样 Next.js API、本地脚本、静态导出可以复用同一套逻辑，也更容易测试和替换。

## 5. 采集层要可解释、可控、可回滚

采集不是简单把搜索结果塞进页面。当前做法保留了几个重要边界：

- `.env` 管理密钥，本地数据库不入库。
- 每次采集写入 `collection_runs`，保留状态、数量和日志。
- 没有 `GEMINI_API_KEY` 时允许创建运行记录，但不写入新信号。
- 去重先看标准化 URL，再看公司、日期、标题和摘要相似度。
- AI 分类结果保留在结构化字段里，便于事后排查。

后续增强采集时，优先增加可观察性和去重质量，再增加采集数量。不要让一次采集大量写入不可解释的重复数据。

## 6. 话题分类要坚持 MECE

“模型、Agent、工具、内容生态、商业化”是本项目的信息架构。经验是默认一条新闻只归入一个主话题，只有拆开会损失事实时才使用跨话题。

分类判断顺序：

1. 模型能力本身是主角，归入模型。
2. 自主规划、调用工具、跨步骤执行任务是主角，归入 Agent。
3. 具体 AI 应用功能或企业工具采用是主角，归入工具。
4. 内容平台、创作者、图文、视频、直播生态是主角，归入内容生态。
5. 广告、收入、定价、采购、合同、部署、融资是主角，归入商业化。

后续如果分类不准，优先修正单条信号或分类提示词，不要轻易新增大类。

## 7. 本地优先，避免误暴露

这个系统默认是本地工具，不是公网服务：

- 本地启动绑定 `127.0.0.1` 更安全。
- `.env`、SQLite 数据库、构建产物不提交。
- `Open Local App.command` 只负责本机便捷启动。
- 采集 API 依赖个人密钥，不应该直接暴露到公网。

如果后续要部署成多人使用版本，需要重新设计鉴权、密钥隔离、任务队列、限流和数据审核流程。

## 8. 后续改动检查清单

提交前至少检查：

- `npm run lint`
- `npm run build`
- `npm run static:export`
- 本地打开 `http://127.0.0.1:3000` 验证主流程。
- 直接打开 `AI-news-dashboard.html` 验证静态快照。

如果改了采集、数据库或报告生成，还要额外检查：

- `npm run local:setup`
- 手动触发一次无密钥或有密钥采集。
- 报告生成和 Markdown 下载。
- 新旧数据是否仍能被 `listSignals` 正确读取。

## 9. 推荐迭代顺序

后续做新功能时，按这个顺序推进最稳：

1. 明确数据契约和样本数据。
2. 更新数据库读写和类型定义。
3. 接好 API route。
4. 在 Dashboard 里做最小可用交互。
5. 同步静态导出。
6. 更新 README 或这份经验文档。
7. 运行 lint、build 和静态导出检查。
