# AIHOT 源码借鉴与本项目演进建议

研究日期：2026-09-29。

对照版本：AIHOT [44578fa](https://github.com/KKKKhazix/AIHOT/tree/44578fa11da55f2e863900752653e0c221f6cf70)；本项目当前工作区，最近提交 `906c6ca`。既有的 `next-env.d.ts` 修改未触碰。

范围：阅读两边的产品入口、采集、数据模型、分类与评分、事件、任务恢复、发布、报告和相关测试代码；只读查询本地 SQLite。没有启动 AIHOT 服务、调用付费模型、运行它的集成测试或验证线上完整数据。因此，下文区分代码具备的机制、当前本地数据现象和建议方案，不把源码中的设计目标当成经过实测的准确率或可靠性。

## 1. 结论与定位

AIHOT 值得复用的不是一套更完整的资讯页面，而是从原始材料到可阅读内容的生产流程：材料留存、判断校准、多来源事件归并、任务恢复、统一发布和增量同步。它已经实现了很多本项目继续独立做资讯聚合时必然会遇到的工程细节。

建议本项目定位为“面向公司、产品和商业化问题的个人研究工作台”：AIHOT 帮助发现行业变化，本项目负责判断这些变化与自己的研究问题有什么关系、发生了什么连续变化、依据是什么。保留“模型、Agent、工具、内容生态、商业化”和公司维度，不必改成另一份泛 AI 日报。

| 路线 | 适用目标 | 本次建议 |
|---|---|---|
| 接 AIHOT 公开 API，再做本地研究层 | 降低聚合维护成本，主要供个人阅读与研究 | 优先验证；另保留少量直接信源和定向补采 |
| 移植有限模块和测试 | 保持自己的采集口径、数据与本地体验 | 与上一条结合；不要移植整套管理后台 |
| Fork 并运行完整 AIHOT 后端 | 自己运营广覆盖资讯产品，承担多信源与持续运维 | 目标变成这类产品时再选；比逐步仿造整套后端更合理 |

默认保留 Next.js 和 SQLite。AIHOT 的 Fastify、PostgreSQL、pg-boss 和独立 worker 互相配合，但更换技术栈本身不会解决证据质量。它的三个进程和分层见[架构源码说明][architecture]。

## 3. 产品侧：从“看新闻”走向“跟踪变化”

### 3.1 用事件组织阅读，保留全部证据

AIHOT 区分一篇材料、一次具体发生的事实，以及包含直接后续进展的事件。多个来源报道同一次发布属于同一事实；随后从预告进入正式可用，是同一事件的新进展，而不是简单重复。网站有事件综述、报道列表与阅读过滤。[事件归组][group]、[事件页面][story-page]提供了具体实现。

本项目最值得新增的产品单位是“事件卡 + 事件详情”，不是更多平铺新闻卡：卡片显示发生了什么、最新进展、来源数量；详情保留一手来源、其他报道、不同说法及研究备注。公司页引用这些事件，不再仅按文章计数。

示意：某产品宣布测试、开放付费用户、调整价格，是三个进展；三家媒体报道同一次开放，不应算成三次公司动作。这只是说明数据关系，不是对现实产品的事实陈述。

### 3.2 在行业重要性之外，加入自己的研究相关性

AIHOT 的默认评分面向关注 AI 的重度用户、产品经理、创业者和轻开发者。其标准压低缺少实质信息的客户 PR、一般招聘、模糊合作和未兑现后果的融资。这对资讯精选有道理，却未必适合公司战略研究：某类招聘、渠道合作或定价变化即使不热门，也可能回答你的问题。[评分提示词][score-prompt]

建议至少区分“行业重要性”和“与关注公司/研究问题的相关性”；证据状态单独显示，不把三者揉成一个高可信分。AIHOT 精选是一个候选来源，不是本项目的最终选材边界。针对自己关注的公司，仍需官方公告、更新日志或少量定向搜索补充。

首屏可优先展示新增事件、关注对象的新进展和待核验内容。报告生成保留为动作入口，不必占据阅读首屏的主要空间。

### 3.3 让公司矩阵表达变化，而非报道数量

保留现有公司和五类话题，但把矩阵逐步改成“状态 + 最近变化 + 证据”，例如产品是否已可用、面向什么用户、价格如何变化、是宣布还是已兑现。没有来源就显示未知；不要把报道多理解为能力强或商业化领先。

“公司近 30/90 天变化”“某个研究问题的支持和反对证据”是适合本项目的差异化方向，是本次建议，不是 AIHOT 已经完整提供的功能。先选一个真实问题做通，再扩展通用研究系统。

### 3.4 补齐人的反馈闭环

提供确认/待核验、纠正公司或话题、合并/拆开报道、写备注几个高频动作，并保存操作时间和修改来源。AIHOT 将人工覆盖和自动判断分开，自动任务不应覆盖人的决定，这比单独一个 `confirmed` 布尔值更可靠。[发布时合成人工覆盖][publish]

收藏、已读可以借鉴 AIHOT 的轻量本地交互；但研究备注和人工判断应落到本地数据库，不应只存在浏览器 localStorage。当前网页能显示已确认状态，不等于已经有完整确认工作流。

## 4. 数据处理：最值得移植的四个机制

### 4.1 原材料、模型结果和人工判断分开

建议逐步形成下面的关系，不要求第一版就照抄 AIHOT 全部表：

```text
来源材料及版本 -> 模型分析及版本 -> 具体事实 -> 持续事件
                         人工纠正与研究备注 -> 引用上述对象
```

材料保留原始 URL、原标题、来源、发现时间、可确认的发布时间、允许保存的正文或摘录、内容哈希。模型分析记录材料版本、模型、提示词版本和处理状态。原始发布者与采集渠道分开，例如“发布者是某公司，采集自 AIHOT”。

AIHOT 的 `upsertMaterial` 集中管理身份、修订与发现记录；另一渠道再次发现同一材料，不会用聚合站自己的标题摘要反复覆盖原始来源。材料真正变化后才产生新修订。[材料入口][materials]

注意：正文抓取成功不等于事实为真；官方原文可以证明厂商宣布了一项能力，不必然证明宣传的效果。AIHOT 的 `body_status=ok`、精选分和实体约束也不能替代主张核验。

### 4.2 URL 去重和事件归并是两件事

同一原文的追踪参数变化应识别为同一材料；不同原文讲同一次发生，应保留原文并关联同一个事实。AIHOT 用 URL/社交帖身份、结构化信息、向量召回和关系判断配合，区分同次发生、同一事件进展、无关和合集；不只判断标题像不像。[URL 身份][url]、[归组][group]

本项目当前数据量不需要专门部署向量数据库。可以先限定时间、主体和动作召回少量候选，再判断关系；加入人工合并/拆分入口。AIHOT 的向量候选本身也是在有限时间窗内筛选，而不是无边界比较全库。

不能直接照抄它的全部边界：默认近期候选窗口约 14 天，而且真正的历史回灌不进入实时事件图。你的长期公司研究需要另行设计历史整理，不能只导入旧材料就期待自动形成几个月的公司演进图。

### 4.3 分开发生时间、发现时间和公开时间

AIHOT 保存来源声称的时间、可信的发布时间、发现时间与时间线时间；超过未来容忍度的来源时间不采信，旧文回灌归档，不冒充今天的新动态。[时间规则][materials]

本项目至少要做到：未知发布时间保留为空；页面必要时明确显示“发现于”；历史回灌不进入最新提醒；同一事件的新进展可以进入最新流，而不是把整段历史都重新推一次。具体 48 小时或 1 小时阈值是 AIHOT 的运营选择，不必原样照搬。

### 4.4 用标注样本校准，不用“感觉分得不错”验收

AIHOT 提供自己的标注格式、开发集/留出集、阈值比较与错例评测。开源只提供两条格式示例，不包含能证明其生产筛选质量的完整金标集。[精选校准][selection]、[评测脚本][eval]

建议从本项目选 100-200 条有代表性的材料，覆盖五类话题、不同公司、一手/二手、边界案例和“不热门但有研究价值”的内容。先标值得关注与否，再比较查准率、查全率、错例类别、处理失败率和成本；调参只看开发集。

AIHOT 默认是同一评分模型独立调用两次，不是两个独立事实核验者；其归组复核模型也需要另外配置才能换成不同模型。可以试验“单次评分，边界样本再复核”是否更适合个人预算，但必须同样本比较，不能预先宣称效果更好。默认 60/65/76 的分级门槛也需要按自己的目标重新校准。

## 5. 后端：借鉴可靠性，不照搬部署复杂度

### 5.1 把运行记录推进到可恢复的阶段任务

本项目已异步采集，但长任务仍在 Next 服务进程内执行。进程重启后的失效标记能解释失败，不能从每条材料的中断阶段继续。

AIHOT 的 worker + pg-boss、状态扫描和重试把采集、正文提取、分析、归组与发布分开。[队列][queue]、[内容任务][jobs]值得借鉴的是：逐条持久化状态、确定重试边界、区分新内容与历史任务、失败不推进成功游标。

个人版可先保留 SQLite，增加一个单独执行采集的 worker 和最小阶段状态；不必同时上 Redis、微服务和多套队列。直接采用 AIHOT 的 pg-boss 则需要接受 PostgreSQL 和相关迁移，不是把一个文件复制过来即可。

### 5.2 为付费调用保存可复用回执

AIHOT 将逻辑请求绑定到输入修订、模型、提示词和参数，先持久化请求，再保存原始响应，最后写业务结果。业务写入失败后可以复用已收到的响应，减少重复付费；超时或进程崩溃后结果未知，不等同于可以无限重发。[调用回执][receipts]

这个思路很适合目前的 Gemini 采集与报告。应测试“已收到模型响应，但尚未写业务表就崩溃”的恢复过程。它不保证所有情况下只计费一次：AIHOT 对未知请求也有一次受控自动重试。它的预算熔断主要按调用次数，不是硬性的金额封顶；本项目可进一步统计每个有效事件的模型成本与人工核验耗时。

### 5.3 让网页、静态导出和报告读同一份内容口径

AIHOT 所有公开出口走 `publication/`，统一处理人工覆盖、是否公开、撤选和时间口径。[公开读取层][publish]

本项目已经有“静态版同源”的工程约定，下一步应落实到共用的读取/投影函数：确定有效标题、来源链接、证据状态、分类、是否纳入报告，然后给 Next 页面、Markdown 和静态导出使用。单用户阶段未必需要额外发布表；先消除多出口对同一字段的不同解释。

### 5.4 直接信源负责确定性采集，搜索负责补缺

先接 AIHOT 与少量官方 RSS/JSON/更新日志，Gemini 搜索保留在发现新源、专题补充和历史研究中。不要每次都让模型重新负责搜索、判断原文 URL、日期和摘要的整条链路。

AIHOT RSS 处理区分正文和订阅摘要，保存 ETag/Last-Modified，配置变化使旧校验状态失效；这些细节可以减少重复抓取和误把截断摘要当正文。[RSS 读取器][rss] 但 X、公众号等付费连接器及其运营信源库不应为了“功能齐全”一次性全部启用。

## 6. API 复用：应按新协议做同步，不只拉最近几天

本机的 [aihot skill](/Users/yuanshikang/.codex/skills/aihot/SKILL.md)描述旧域名的 `/api/public/*`。此次开源快照则提供 `/api/v1/` 和新同步契约；具体接入前应再核对部署站的 OpenAPI，不能沿用旧 skill 的字段、UA 约束和时间窗口假设。[v1 实现][v1]

- `/api/v1/selected/snapshot`：分批建立当前精选集合的完整本地快照，不只是 items 接口的近 7 天窗口；它不是所有未精选历史材料的全量导出。
- `/api/v1/selected/changes`：按游标接受新增/修改和 `remove`，游标所属账本失效时重新快照。
- `/api/v1/items`：适合滚动窗口检索，不代替持续资料库同步。
- 事件详情另有接口；精选同步载荷不是完整正文库，也不等于包含整个事件关系图。

本地用 `provider + externalId` 做幂等标识；游标与成功写入在同一事务提交，重放不会重复插入。上游修改更新原始快照，不覆盖研究备注；`remove` 表示离开上游精选集合，应标记状态，不直接删除自己引用过的研究记录。快照重建也必须保留本地标注。

上述是仓库支持的协议能力，本次没有验证当前部署站的历史覆盖、完整同步量或可用性。正式替代现有采集前，应先做少量只读试接和数据质量抽样，并保留最后成功同步时间与来源故障状态。

## 8. 报告生成与落地顺序

AIHOT 的报告先挑材料、做事实去重、控制版面，再让模型引用限定编号；程序回填真实条目和链接。它还处理跨刊期完成的内容，避免仅按文章原始日期导致漏报。[报告编排][reports]

本项目应先改为“候选集 -> 事件去重 -> 相关性/覆盖选材 -> 固定证据编号 -> 生成 -> 检查引用”，保存实际使用的材料 ID 和版本。总样本量与报告实际覆盖量分开显示。没有材料支持时只列已知事实，不输出固定趋势判断。引用编号正确只是结构正确，重要结论仍要检查材料是否真的支持。

| 批次 | 内容 | 验收条件 |
|---|---|---|
| 1：证据与输入 | 修正搜索页/可信度语义、未知日期；保留材料身份和原始快照；小范围试接 AIHOT 同步 | 搜索链接不标直达原文；未知日期不变今天；相同导入不新增重复记录；上游更新/撤选不丢本地备注 |
| 2：事件与恢复 | 多报道归入事件、人工纠错、持久化阶段任务、模型响应回执；用标注集比较筛选与归组 | 同一发生三篇报道显示一个事件并保留三份材料；后续进展不被丢弃；人工纠正不被重跑覆盖；收到响应后的业务重试不重复调用模型 |
| 3：研究输出 | 公司变化页、与上次报告的差异、可追溯报告；统一静态与动态出口 | 每条关键判断能回到材料版本；报告覆盖数量准确；新增/变更/延续可区分；没有证据时不补固定结论 |

选一个公司或一个研究问题贯穿三批完成试点，记录实际省下的阅读时间、采纳率、漏掉的重要事件和成本，再决定扩大信源、加入向量召回或迁移 PostgreSQL。暂缓大规模来源扩张、独立向量库、多 Agent 编排以及纯展示性质的新地图。
